目的は手法を思い出すことではなく、問題の特徴 → 表現 → 初期解 → 探索 → 近傍 → 高速化 → 検証を短時間でつなぐこと。まず正しいgreedyとscore breakdownを作る。

開始チェック

問題を読んだ直後

  1. 入力サイズ、操作上限、出力上限、時間、メモリ、interactiveか
  2. スコアの向き・丸め・0点条件・ケース間集約を数式化
  3. score = Σ local contribution に分けられるか。各decisionがどの項に依存するかを図示
  4. hard feasibilityとsoft penaltyを分離。常に実行可能解を保てる表現は何か
  5. 状態変数、decision variable、対称性、可換性、分離可能性、冗長性
  6. trivial boundとgreedy baseline。1ケースを手計算しscorerと一致させる
  7. full score、delta score、hashをランダム操作列で照合
  8. 100 seedの中央値と分布、プロファイル、探索反復数を記録

最初に作るscore breakdown

まず: 総scoreだけでなく、距離・違反・未処理・資源・終端価値など寄与別にログする。改善が何を犠牲にしたか見える。

依存グラフを作り「変数xを変えると再計算する項」を列挙。prefix/suffix、局所キャッシュ、dirty flag、定期full再計算の候補を決める。

Problem → Method Decision Tree

逐次的に解を構築する？ ├─ Yes │ ├─ 各深さの分岐候補を絞れる？ │ │ ├─ Yes → greedy baseline → fixed/time-limited Beam │ │ │ 深さ間で良い候補の出現が偏る → Chokudai │ │ └─ No → candidate reduction / dominance / pruning │ └─ 先の価値をsimulationで比較でき、分岐が中程度？ → MCTSを小規模検証 └─ No（完成解を作れる） ├─ 局所変更で実行可能性を保てる？ │ ├─ Yes → HC → SA → ILS / multi-start │ └─ No │ ├─ 一部を壊して貪欲に直せる？ → destroy-repair / LNS │ └─ 表現を簡略化 → surrogateを探索 → 最後にrepair └─ 変数が巨大？ → block / coordinate / coarse-to-fine greedyが強い → tie-break / randomized greedy / parameter search / greedy+LS を先に試す 探索1回が重い → 近似評価・候補制限・差分化。賢さ×1回より quality×iterations を測る

症状から探す

スコア計算が重い

最初: deltaの依存範囲を列挙。

  1. 変更部分だけのlocal contribution
  2. prefix/suffix、区間集約、前後からの再計算
  3. dirty flagとキャッシュ
  4. 安いsurrogateを普段使いし、真値を定期計算
  5. 複数moveをまとめて再評価

危険: cache invalidation bug。ランダム差分テストを常設する。

SAが改善しない

最初: delta bugと近傍を疑う。温度調整はその後。

  1. 同一状態でfull scoreとincremental scoreが一致するか
  2. 受理率を近傍別・時間帯別にログ
  3. 近傍が弱すぎる/強すぎる、実行可能性判定でほぼ棄却されていないか
  4. 初期温度で悪化moveの20–80%程度を受理するかを観察
  5. 終温度でほぼhill climbになるか
  6. 表現が良い解同士を局所moveで結べるか

次: relocate↔swap↔segment↔destroy-repair、adaptive selection、restart/reheat。

Beamが遅い / 幅を増やせない

  1. State copy bytes × generated nodesを計算
  2. 全sortをnth_elementに変更
  3. action/parentだけ保持、layer workspaceを再利用
  4. hashを差分更新。重複除去が得点に見合うかA/B
  5. 候補生成を上位Kに制限、深さ別width
  6. rollbackで親を順に適用しchild評価

幅を増やすと、多様性低下・評価関数の偏り・時間切れで悪化もする。

変数が多すぎる

重要変数だけ選ぶ、block coordinate、coarse-to-fine、低頻度変数を固定、destroy-repair。詳細を探索せず、順序・集合・anchorだけ最適化して最後にgreedy/DPでmaterializeする。

改善したはずなのに順位が安定しない

同じseedでpaired comparison。meanだけでなくmedian、win/tie/lose、relative/geometric mean、bootstrap CIを見る。極端seedをscore breakdownし、ケース群を構造で層別化する。

ローカル実行時間が揺れる

benchmarkは単独process、warmup後に同一caseを複数回。physical coreへaffinity固定、SMT siblingを同時使用しない。turbo/温度/電源プラン/background/WSL・Docker差を記録。throughput時間を提出時間と解釈しない。

greedyがかなり強い

複雑化の前に:

tie-breakの特徴量化、ランダム化、候補上位Kから選択、parameter sweep、multi-start、最後だけlocal search。greedyの選択理由をログして「誤る局面」だけを再探索する。

実行可能性制約が探索を殺す

常にfeasibleな符号化、repair付きmove、制約を保つcycle/Kempe-chain、違反量を段階的penaltyにする。拒否率を原因別に測る。soft化する場合、終了前に必ずrepair可能か確認。

問題構造 → 初手

順列・巡回・訪問順

greedy construction → swap/insert/2-opt → SA → segment/LNS

位置間寄与ならswap、隣接辺寄与なら2-opt、precedenceが強ければremove-reinsert。linked listは挿入が軽いがランダム位置参照とcopyに注意。

配置・割当

greedy placement → relocate → swap → block move → SA/LNS

各要素の所属先とbin集約を持つ。空き容量・局所costを差分化。関連要素をまとめたblockは谷を越えるがdeltaが重い。

スケジューリング

priority heuristic → single reassignment → swap → critical region optimization

全区間ではなく遅延・資源競合のcritical regionを選ぶ。prefix/suffix状態で区間だけ再simulate。

長い操作列

greedy → candidate-reduced Beam → 局所区間の再探索

出力列全体でなくparent/actionを保存。状態の同値性をhashに落とせるならdedupe。終盤だけ評価精度を上げる。

巨大空間・詳細生成が重い

coarse solution → important variables → restricted optimization → exact/greedy repair

探索変数をanchor、集合、順序へ落とし、経路や細部は都度近似または最後に生成。surrogateと真scoreの順位相関を測る。

逐次意思決定＋rollout

分岐が中程度、horizonが短〜中、途中状態の価値がrolloutで識別できる場合だけMCTS候補。分岐巨大ならprogressive widening、良いpriorがあればPUCT。遷移copyとrollout誤差が大きいならBeam/greedyを優先。

近傍設計集

近傍適する表現 / 計算量探索性・注意
swap配列・割当。典型O(1)〜依存項数feasibleを保ちやすい。順序の大移動は遅い
insert / relocate順列・bin。配列O(length)、linked list O(1)順序/所属を強く変える。影響区間のdelta
reverse / 2-opt経路。対称距離ならO(1)交差除去に強い。有向・位置依存costでは内部再計算
3-opt / segment経路・操作列。O(1)〜segment長強いが候補数と実装bug増。2-opt飽和後
block swapcluster化された列/配置谷越え。block選択を構造に寄せる
single/multi mutationベクトル・離散パラメータmultiのサイズを温度/停滞で変える
boundary shift区間分割・領域局所deltaが容易。merge/splitも併用
destroy-repair強制約の割当・経路強いexploration。repair qualityと時間を測る
Kempe-chain / cycle彩色・matching・保存制約feasibilityを保ちつつ大変更。連結成分生成cost

近傍の評価表

各近傍について「試行数、feasible率、受理率、改善率、平均delta、ns/試行、bestへの寄与」を時間帯別に取る。強い近傍ほど良いとは限らず、改善/秒で選ぶ。最低確率を残したadaptive選択で未探索化を防ぐ。

探索の使い分け

HC / SA / ILS / LNS

HCはbaselineと近傍debugに最適。局所的な良さが連続し差分が軽ければSA。restartで盆地が変わるならILS。局所moveで谷を越えられない強制約・cluster構造ならLNS/ruin-recreate。Tabu/LAHC/threshold acceptingは、SAの温度調整より履歴/閾値が扱いやすい場合に知識候補とし、まず薄い実装でA/Bする。

Beam / Chokudai

Beamは逐次構築、終端までの評価が途中状態から相関、候補削減が可能な場合。Chokudaiは良いnodeが深さごとに不均一に発生し、時間内に各depthを繰り返し掘る価値がある場合。通常Beamの方がcache localityと実装の単純さで勝つことも多い。

hash collision: 64-bit一個は高速な近似。誤除去が許せないなら128-bit/代表状態の軽い照合。重複除去自体のcostも測る。

MCTSを選ぶ条件

向く: rolloutが最終価値を識別、同じ木を十分再訪、確率的結果、行動priorが有用。向かない: 分岐巨大、horizon長大、rolloutがほぼnoise、遷移が重い、決定論的でBeam評価が強い。transpositionは合流が多い時だけ。cycle・深さ依存価値・共有統計のperspectiveに注意。

知識として持つが標準実装しないもの

Branch and Bound、limited discrepancy、Tabu、GRASP、LAHCなどは問題依存のbound・memory・constructionが本体。巨大frameworkには入れず、該当構造が見えた時にテンプレートを直接改造する。

高速化の判断

State管理

小さいtrivially-copyable stateならvector copyで十分。大きければundo log、reversible operation、parent/action、workspace再利用。copy-on-writeは参照管理costがあるため共有が多い時だけ。allocationをloop外へ。

set / hash / candidate

小さい密なkeyは配列・timestamp・bitset。挿入削除のdense universeはdense/sparse set。unordered_mapは反復数が十分なら使う。reserve、custom hash、flat representationはprofileで支配的な時だけ。priority queueはlazy deletion、上位Kだけならnth_element/bucketも検討。

grid / graph

gridを1次元flatten、番兵またはneighbors事前計算、BFS queue/distを再利用。全点間距離を前計算できるサイズか確認。BFS/0-1 BFS/Dijkstraを素直に選び、incremental shortest pathは更新が局所かつ再計算が実測bottleneckの場合だけ。

hot loop

xoshiroの整数/real生成、modulo rejection、exp、chrono頻度、branch、state copy、allocation、virtual/std::functionをmicro benchmark。Timerは256回に1度などでclockを読む。acceptanceのexpは悪化moveだけ。最適化は探索loop全体のprofileで再確認。

失敗パターン

SAがgreedyに負ける

初期解を壊すだけの近傍、surrogateが真scoreと不一致、温度以前にdelta bug。greedyからHCを行い、改善moveの存在と到達可能性を先に確認。

Beam width増で悪化

時間当たり深さ不足、同型候補で多様性消失、弱い途中評価のbias増幅。widthだけでなく候補制限・dedupe key・depth別配分をA/B。

高精度評価で反復激減

評価精度の相関向上とiterations/secを分離。二段階評価、periodic true score、終盤だけ高精度を試す。

少数seedで改善を誤認

同一seed paired、100→1000へ段階拡大、bootstrap CI。チューニングに使ったseedとholdoutを分ける。

並列時間を信じる

cache/memory/SMT/thermal競合を含むthroughput測定で単体実行時間を推定しない。benchmark.pyを単独・affinity固定で使う。

複雑な初期解に時間を使いすぎる

初期解改善が最終scoreに残るか、探索時間減を上回るかを測る。単純greedy+長い探索とpaired比較。

過去例からの一般化

局所group再計算（AHC049型）

変更が少数groupに閉じ、group sizeが小さいなら、そのgroupだけ真scoreを再計算する。relocate/swapが自然。前後どちらから計算するとdependencyが短いかも確認する。

時間依存surrogate（AHC047型）

生scoreが大項目だけを早期に支配し候補を不可逆に消す時、序盤は各項を均す変換、終盤は真scoreへ連続的に戻す。最終目的と異なるため、真score bestを別保持する。

簡略表現＋Beam→SA（AHC043型）

詳細経路を探索変数にせずanchor位置・順序だけを探索し、具体化はgreedy。短いBeamで多様な初期候補を作ってSAへ渡す。表現削減とhybridは巨大状態に一般化できる。

集合move＋高価subproblem分離（AHC020型）

add/removeだけでなくexchangeで探索の連結性を上げる。networkなど高価な従属問題は、毎回近似/キャッシュするか最後だけ解くかを、順位相関と反復数で決める。

順列insertの表現変更（AHC059型）

insertが主近傍なら配列shiftがbottleneckになり得る。linked list＋alive/position補助で局所更新。ただしランダムindexや全走査が増えるなら配列が勝つためmicro+loopで比較。

段階的時間配分＋exact finish（AHC066型）

前半はmacro/大構造、後半は順序など細部へmove頻度を移す。候補を複数残し最後に小規模DP/repair。異なる時間尺度の変数を同率で動かさない。

Topcoder MMからの運用原則

visualizer/scorerを最初に自動化し、local/server速度差を校正。latest submission依存など各contest規約を読む。探索法より実験の再現性、seed管理、変更履歴が長期改善を支える。

評価とbenchmark

スコア評価

tester/run.py --solver ./solver --cases 0-999 --jobs 6 --cores 0,2,4,6,8,10

目的はthroughput。stdout/stderr/score/time/statusを保存。A/Bは同一seedでcompare.py A.csv B.csv。ratioは正値かつ尺度に意味がある時だけ。

速度評価

tester/benchmark.py --solver ./solver --input in/0000.txt --core 0 --warmup 2 --repeat 15

median, p25/p75, min/max, CVを確認。CVが高ければ改善差を論じない。初期化・出力・safety marginを含むend-to-end時間も別途測る。

Linux / WSLのaffinity

lscpu -e=CPU,CORE,SOCKET,NODEでphysical coreを確認。Ryzen 6C/12Tなら同一COREのsiblingsを避けた6 process以下から開始。WSL、Docker、antivirus、Windows電源設定の影響を結果metadataに残す。
