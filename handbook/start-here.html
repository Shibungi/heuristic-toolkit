READ THIS FIRST

コードを書く前と、遅いときに見る入口

各手法を暗記する資料ではありません。目的関数の向き、状態、1手、採否、計算量を順番に確認し、手法が問題に合うかを判断するための読み方です。

01 / PROBLEM

最初に答える3問

何を良くするのか

最大化か最小化か、実行不可能条件は何かを数式か日本語で書く。ライブラリの内部スコアと問題のスコアが逆向きなら、符号を反転する。

1手で何が変わるのか

State、Action、変更される評価項を列挙する。全再計算せずに差分だけ更新できるか、apply後にundoで完全に戻せるかを小さい入力で検査する。

1秒を何が使うのか

反復回数、1反復の候補数、Stateコピー量、評価計算、木の走査を分けて測る。アルゴリズム名ではなく、実測で支配している処理を直す。

02 / RUN

通常実行とバグ調査を分ける

通常の速度を見るとき

./build.sh release
./run.sh in/0000.txt

run.sh は使用する実行ファイル、入力、出力先、制限時間を最初に表示し、実行中は1秒ごとに経過時間を表示する。既定の制限時間は5秒で、HT_TIMEOUT=10 のように変更できる。

メモリ破壊や範囲外アクセスを探すとき

HT_MODE=debug HT_TIMEOUT=30 ./run.sh in/0000.txt

debug版は AddressSanitizer、UndefinedBehaviorSanitizer、_GLIBCXX_DEBUG を有効にする。意図的に遅く、メモリも多く使うため、提出速度の測定には使わない。

03 / POSTMORTEM

AHC070で長時間になった理由

意図された1.85秒

現在のmain.cppはTimer(1.85, 0.05)で停止するまで改善探索を続ける。release版が約1.82秒かかるのは停止条件どおりで、run.shが複数caseを実行しているためではない。

1試行が重い

1試行で近傍を4種類試し、そのたびにget_scoreを全計算する。評価は10,000個の操作を順に処理し、各位置追加後に100×100盤面の距離更新を行う。ここが探索本体の計算時間を使う。

debug版がさらに遅い理由

安全検査の追加に加え、Timerは4試行ごとにしか時刻を確認しない。1試行がdebug版で極端に重いと、次に時計を見るまで停止予定を超える。速度測定はrelease、debugはバグ調査に分ける。

04 / SCORE DIRECTION

最大化・最小化を取り違えない

HillClimbing

この実装は最大化専用。delta = 新score - 現score とし、delta >= 0 の手だけ採用する。最小化問題ではscoreを負にするか、専用ループを書く。

SimulatedAnnealing

maximize=true/false で向きを指定できる。ライブラリへ渡すdeltaの定義と設定を一致させる。

Beam / Chokudai

Beamは大きい評価値を残す構成、Chokudaiは比較器で順序を決める。距離最小化なら例のように-distanceを最大化する方法が単純。

05 / EXAMPLES

過去問コードの読み順

  1. 冒頭コメントで、問題と目的関数の向きを確認する。
  2. State が何を保持し、何を省略しているかを見る。
  3. Action と、1手で変更される箇所を見る。
  4. 候補の採否・上位選択・重複除去を見る。
  5. 返す解と、簡略例として省略した制約を確認する。

例は提出解のコピーではなく、各ライブラリの役割を小さく切り出した教材である。冒頭の「制限」を読んでから実戦用へ拡張する。

AHC002

Timer / RNG / FastSet / GridIndex / Logger。重複タイルを避けながら経路得点を最大化する。

AHC004

SA / HC / bitset / Zobrist。文字列を盤面へ配置し、含まれる対象文字列数を増やす。

AHC007

DSU。オンラインで辺を選び、連結性を意識しながら採用辺長を小さくする。

AHC009

Beam / TreeBeam / Chokudai / MCTS / BFS。確率的に失敗する移動列でゴール到達を狙う。

AHC021

UndoLog。三角盤面の局所swapをapply / undoし、違反を減らす。
